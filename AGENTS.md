# Instructions for coding agents

This repo is a **private** Buzz desktop plugin (`claude-subscription`) that registers an agent harness
whose turns run on the owner's own signed-in Claude Code, through the Claude Code ACP adapter. Read
[README.md](README.md) first.

## Hard rules

- **The plugin stays private.** Never publish it, attach a build anywhere, make the repo public, or
  add a way to share the plugin: subscription sign-in in third-party products needs Anthropic's
  approval.
- **Share lists Buzz's own Claude, never this plugin.** Buzz's agent menu offers Share for a type
  with `exportShared` (`src/settings.ts`); a share's instructions come from `carry`. It names Buzz's
  `claude` runtime and the model, so whoever adds the agent runs Buzz's Claude harness on their own
  sign-in. Never list a runtime, provider or setting that points at this plugin or the workspace.
  Don't add `importShared`: Buzz imports a listing as the first type that accepts it, which would
  take Claude listings from Buzz's own harness.
- **One self-contained module.** Buzz loads `plugin/plugin.js` from a blob URL: no runtime imports, no
  CSS or asset files, no code splitting. `build.mjs` and `scripts/check.mjs` enforce it.
- **React comes from Buzz.** Never import `react` or `react-dom` at runtime. JSX compiles to
  `React.createElement` against `src/react.ts`, set from `ctx.react` in `apply`. Tests may import React.
- **Types only from Buzz.** `src/buzz.ts` re-exports Buzz's type-only plugin API (`@buzz/author`),
  generated by `npm run types` from the Buzz release `BUZZ_REF` in `scripts/types.mjs`. Never import
  anything from it at runtime.
- **No Buzz UI components.** Buzz exposes none to plugins. Build UI in `src/ui.tsx` with Buzz's global
  `buzz-*` classes and design tokens (`var(--space-2)` etc.), matching Buzz's own markup: choices are
  `ChoiceRow` menus in a `SettingsGroup`, never free text where Claude Code can list the values
  (models, thinking levels and permission modes come from `src/models.ts`).
- **The Settings tab places the host's Harness row** (`settingsHost.typeControl`) first in its identity
  part, or the agent can't change type; it is split (`splitSettings`) into identity and runtime parts.
- **Synced settings are text only**, from `syncedSettingsSchema`: Buzz refuses a non-text value or an
  unknown key, and an agent whose settings sync can't save or start without them.
- **Commit the build.** After changing `src/`, run `npm run build` and commit `plugin/plugin.js`;
  `npm run check` fails if it's stale.
- **Install and go.** Beyond Claude Code signed in and Node.js 22, nothing is set up by hand: the
  manifest runs the adapter with `npx`, pinned (`npx -y …@x.y.z`). To change the adapter, bump it in
  `plugin/manifest.json`, run the live test, and update `scripts/check.mjs` and `src/claude.test.ts`.
- **The manifest asks only for the adapter, `mcp` and `files`.** `mcp` serves the Buzz tools to
  Claude as the agent; `files` reads uploads the agent is asked to make and Claude Code's
  transcripts. A `manifest.host` change needs the owner's approval on update in Buzz; keep it
  minimal, and update `scripts/check.mjs` and `src/claude.test.ts` with it.
- **The subscription login, never a key.** Keep `ANTHROPIC_API_KEY` out of Claude's environment
  (`ENV` in `src/claude.ts`).
- **Only a checked session UUID names a transcript file** to read (`src/transcript.ts`).
- **Copied Buzz code stays close to Buzz.** `src/acp/`, `src/sessions.ts` and
  `src/transcript-model.ts` are Buzz's own (Apache-2.0): keep changes small and note each in
  [NOTICE.md](NOTICE.md).
- **Live tests run in a temp folder.** The live test works in a new folder under the system's temp
  folder and uses the subscription's usage; its Claude Code session stays in `~/.claude/projects` like
  any other. Never run a live test from a self-restarting launcher (`launchctl submit`, a watch loop).

## Layout

| Path | What it is |
| --- | --- |
| `src/index.tsx` | `apply(ctx)`: registers the agent type, its tabs and icon |
| `src/runtime.ts` | Turns Buzz deliveries into Claude turns, on the harness kit |
| `src/acp/` | Buzz's ACP client, copied (see NOTICE.md) |
| `src/claude.ts` | The adapter's ACP hooks: model, thinking level and permission mode selection |
| `src/models.ts` | Lists models, levels and permission modes from a short-lived adapter session |
| `src/settings.ts` | Config, defaults, synced settings, `carry`/`adopt` across harness changes, and `exportShared` (Share) |
| `src/sessions.ts` | Each agent's conversations and their Claude sessions, in local storage |
| `src/tabs.tsx` | New agent fields, Settings tab (identity and runtime parts), Activity tab and transcript view |
| `src/transcript.ts` | Reads Claude Code's `~/.claude/projects/<workspace>/<session>.jsonl` into Buzz's turn model |
| `src/transcript-model.ts` | Buzz's turn-transcript model, copied |
| `src/ui.tsx` | Buzz-styled controls |
| `src/icon.tsx` | The harness's icon, drawn for this plugin (not Anthropic's logo) |
| `src/react.ts` | React from Buzz (`ctx.react`) |
| `src/buzz.ts` | The Buzz plugin API types this plugin uses, from `@buzz/author` |

## Checks

- `npm test`: unit tests in `src/`, including loading the built `plugin.js` and rendering every tab.
- `npm run typecheck`, after `npm run types` (or `node scripts/types.mjs <buzz-app checkout>`).
- `npm run check`: typecheck, tests, manifest, icon and build freshness.
- `CLAUDE_LIVE=1 npx vitest run src/runtime.live.test.ts`: a real turn on the Claude Code login, with
  a stand-in harness kit and the Buzz tools served over loopback MCP (`CLAUDE_MODEL` picks the model,
  default `haiku`). Nothing reaches Buzz.
- Before a release, also try the change in Buzz itself: install from `plugin/`, switch an agent to
  Claude (subscription), mention it, and check its reply and its Activity tab.

## Releases

1. After a Buzz update, set `BUZZ_REF` in `scripts/types.mjs`, run `npm run types` and fix any type
   errors.
2. Update `version` in `package.json` and add a `## X.Y.Z (YYYY-MM-DD)` section to `CHANGELOG.md`.
3. `npm run build && npm run check`.
4. Merge to `main`. The Release workflow (`.github/workflows/release.yml`) releases each version
   that has no tag yet: it runs the check, then creates the tag `vX.Y.Z` and a GitHub release with
   that changelog section. A merge that doesn't change the version releases nothing. Never tag or
   release by hand, and never attach a build: the plugin is installed from a checkout's `plugin/`
   folder.
